---
name: cursor-hook-messages-queue-not-steer
description: Cursor hook messages queue instead of steering; preToolUse deny + agent_message is the only mid-generation channel, and hooks never see the user's shell env
metadata:
  type: reference
---

Live-probed against Cursor agent CLI 2026.07.23-e383d2b (the newest build; the install endpoint pins it), 2026-07-29, with stub hooks in a scratch workspace on composer-2.5:

- `postToolUse` `additional_context` is appended to the stored tool result as a `<system_reminder>` block immediately, but the in-flight generation never acts on it: an urgent injected instruction after tool 1 of 3 was ignored through two further tool boundaries and the final reply. The model effectively reads it only from the next generation onward. Owner observed the same in real sessions (a User's Claim: Cursor hooks fire as queue, the Cursor default). The likely mechanism is server-side generation continuation that does not re-read stored history mid-run.
- `stop` `followup_message` enters the follow-up queue and auto-submits as the next user message once the agent is idle; `loop_count` increments per auto-follow-up and the per-script `loop_limit` (default 5) caps it. Delivery at idle is prompt in practice, but it is queue semantics, and a forum bug report shows queued followups can wedge after background-task waits.
- Cursor's hook output schemas (raw docs pulled 2026-07-29, full field tables) contain NO delivery-mode field anywhere: no steer/queue/interrupt switch exists for hook-injected messages. The queue-vs-steer choice exists only for human-typed messages (Cursor Settings -> Chat -> Queue messages).
- The one true mid-generation channel is `preToolUse` returning `permission: "deny"` with `agent_message`: the denial reason reaches the model inside the running generation. Probed twice in one generation; the model processed the injected message and re-ran the denied command about 2 seconds later, both times. `user_message` shows the correction in the client. This is why v3.13.0 delivers live-monitor corrections on two channels: `additional_context` as before (guaranteed next-generation delivery, sole channel on installs without the `preToolUse` entry) plus a pending-correction file consumed by a fast `preToolUse` hook for mid-generation steer (same-conversation, same-generation guard; stale states consumed and dropped because the context channel already carried them). An adversarial review round (2026-07-29) caught the first cut making the pending file the ONLY channel, which silently killed the live monitor on stale installs and destroyed end-of-generation corrections; never regress to single-channel.
- `generation_id` on pre/postToolUse is per-turn: live probes show it distinct from `conversation_id` and changing between turns of one conversation. A bundle-reading review pass mis-traced the minified CLI and concluded it equals the conversation id; the live probe logs refute that. Trust live payload logs over minified-bundle tracing.
- Cursor launches hook subprocesses with a constructed environment, not the user's shell env: with `CORRECTIONGUY_MODEL` exported to an intentionally invalid value in the CLI's environment (propagation into the CLI process separately verified), the stop review still ran on the default model. `CORRECTIONGUY_*` shell exports are dead config in Cursor; defaults apply. Unverified follow-up: docs say a `sessionStart` hook can return `{env}` that joins later hook environments, which could carry configuration if it can read values from somewhere.

**Why:** The owner reported Correction Guy's Cursor corrections firing as queued messages when they need to steer, and asked for steer delivery. Every plausible steer surface had to be checked (docs, changelog, forum, shipped CLI source, live probes) before concluding deny-with-message is the only real channel.

**How to apply:** Never expect `additional_context` to influence the generation that triggered it; treat it as next-turn context. Deliver anything time-critical through the `preToolUse` deny path. Re-verify on new Cursor releases: a dead `"claude-plugin"` cwd case and the hook validator both hint the surface still evolves, and a native steer field would obsolete the deny workaround. See [[cursor-plugin-hooks-never-execute]] and [[no-unapproved-shared-config-mutation]].
